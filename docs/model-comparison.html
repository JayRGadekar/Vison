The headline is that 2.2 is faster despite being roughly four times the parameters. Its VAE compresses space 16× against 2.1’s 8×, so there are a quarter as many latent pixels to decode — and on this hardware decode, not diffusion, was the expensive half.

The finding

Same model, same prompt, same seed

The only differences are resolution, guidance, and whether the standard Wan negative prompt was supplied. Vison was sending its generic Stable‑Diffusion‑era defaults to every model.

A model far outside its trained resolution fails silently and looks exactly like a broken pipeline. That is why the registry now carries default_width, default_height, default_guidance and default_negative_prompt per model, and why the controls move when you switch models.

What was fixed

Three defects surfaced by running this

01

The VAE decoded every frame in one graph

stable-diffusion.cpp sizes its tile in latent units and clamps it to the latent dimension. Wan 2.2’s 16× compression makes a 320×320 request a 20×20 latent — smaller than the default 32×32 tile — so it concluded one tile covered everything and asked for 7.8 GiB on a 5.8 GiB card. Vison now picks a tile count from measured MB‑per‑tile‑pixel, which is independent of any VAE’s compression ratio.

02

Out-of-memory never retried

The queue treated an OOM as final, on the reasoning that a second attempt would fail identically. That stopped being true once the backoff level started feeding the tiling plan. Upstream cannot help here — its own retry refuses to act once tiling is already on, so it can turn tiling on but never make it finer. A 480×832×5 clip went from OOM to 88 seconds.

03

Video reused the image aspect-ratio presets

Every preset was 1024‑based, so asking for 16:9 video meant 1024×576 — 1.5× the pixels of Wan’s documented size, and a quarter‑hour per clip if it fit at all. Ratios now redistribute the model’s own pixel budget, so 16:9 resolves to 848×480.

Still open

One thing this did not fix

A GPU device loss during VAE decode killed the backend process outright, mid‑teardown, with no error reaching the client — so the device‑loss retry never ran. The process now installs terminate and SEH handlers and unbuffers stderr, but the crash has not reproduced since, so the handlers are instrumentation, not a proven fix. Finer tiling makes each submit shorter and should make the loss itself much rarer.
